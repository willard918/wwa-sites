# Website prototype (Willard Williams Architect / Pacific Living Solutions / Trillium)

Single-page site, dark "Porsche" style. Tagline: **Precision, at home.**

## Files
| File | What |
|---|---|
| `src/index.src.html` | The page (HTML, CSS, page script). Edit this. |
| `src/adu.js` | ADU panel rules (mirror `adu/adu_model.py`) + three.js scene, still renderer and OBJ export. |
| `lotcheck/` | Lot check: backend `server.py` (+ `geom.py`, `rules.py`) and its UI `lotcheck.js` / `lotcheck.css`. See **Lot check** below. |
| `build.py` | `python build.py` inlines `adu.js` and the lot-check UI and writes `index.html` (one file, opens anywhere). |
| `index.html` | Built output. Do not edit by hand. |

## Lot check (added 2026-11-03)
Address -> parcel -> state ADU baseline -> which units fit -> a report with an SVG lot plan.

**Run it:** `python lotcheck/server.py` (port 8787; `--port N` to change), then open `http://127.0.0.1:8787/`. The server serves the built `index.html` itself, so page and API share an origin. A page opened from `file://` calls `http://127.0.0.1:8787`; the preview pane blocks that, so use the served page. CLI: `python lotcheck/server.py --check "150 Sugar Pine Rd, Trail, OR 97541"` (add `--json` for everything). Offline tests: `python lotcheck/test_geom.py`. Python 3.10 stdlib only.

**Pipeline** (`lotcheck/server.py`): US Census geocoder (address, county, city limits; no key) -> county adapter -> parcel polygon -> geometry (`geom.py`) -> verdict (`rules.py`). If the Census doesn't know the street (new subdivisions), Jackson County's own address records are used instead.

**Verified working (2026-11-03):** Phoenix-area OR lot (Eagle Point city limits), unincorporated Jackson Co. lot (Trail, zoning WR), Del Norte CA and King WA addresses (state baseline, "not enough data"), an Idaho address (outside service area), and junk input. Geometry unit tests pass. Results arrive in under about 1.5 s per lot after the first call (the first call took up to a few seconds on a large lot).

**Ground slope (added 2026-11-24):** `lotcheck/terrain.py` samples USGS 3DEP elevation (1 m lidar, free, one batched request per 400 points) on a ~10 ft grid over the lot, smooths it and computes slope. A unit is only placed where the average slope under it is <= 15%, no more than 5% of its footprint is steeper than 20%, and the spot can be reached from the street frontage over ground <= 15% (flood-fill from the frontage cells; assumes the street side is right). Limits live in `terrain.THRESHOLDS` and are placeholders to confirm with the builder. If the elevation service fails the result is 'Needs review' and letters are not generated. Skyview Dr, Medford (median slope 31%, 106 ft of fall) is ruled out; flat Talent lots still fit. Offline tests: `python lotcheck/test_terrain.py`. `python outreach/letters.py recheck` re-runs every stored letter with the slope check and marks lots that no longer qualify `dropped` (not printed, no landing page). `letters.py csv` refuses steep lots.

**Data sources:** Census geocoder; Jackson County GIS `Property/Taxlots2` (weekly refresh; owner names are never read or returned).

**Assumed, not verified (all shown in the report):**
- Setbacks: front 20 ft, side/rear 5 ft (OR, WA) or 4 ft (CA). These are placeholders, not code lookups. The street side is the lot edge nearest the geocoded point; for address-record fallbacks the street is unknown, so 20 ft is applied to every edge (cautious). Corner lots' second street side is not detected.
- Existing buildings, easements, flood/fire zones and utilities are not in the data, so the unit may collide with a house that is not shown.
- Oregon's ADU mandate covers cities over 2,500 residents; the city's population is not checked. County thresholds and rural rules (e.g. SB 391) were not verified.
- California section numbers and review timelines and the Washington size rules were not verified; only the points listed in `rules.py` were read from search results (see its sources). Re-verify before relying on them.
- Land-use class labels (100/101/400/401) follow the Oregon DOR scheme from memory; other codes show their raw number and give "Needs review".
- County zoning appears only where the county layer has it (unincorporated land and some fringe lots); city zoning (Phoenix, Eagle Point, Shady Cove...) is not connected. The report says so.
- The county's mailing city can differ from the actual city limits (e.g. "Phoenix" mail on a lot inside Eagle Point); the report shows the Census city limits and notes the difference.

**To add a county:** write an adapter in `server.py` that returns `{id, site_address, acres, use, improved, zoning, polygon_lonlat, source}` and register its FIPS in `ADAPTERS`. Public ArcGIS REST point queries with `inSR=4326&outSR=4326&distance=25` work the same way. Candidates not yet tested: Oregon statewide taxlots (gis.odf.oregon.gov, inconsistent currency), Douglas Co. OR (Roseburg), Del Norte Co. CA, WA counties.

**Deploying:** a static host cannot run this. It needs a small Python host (or a serverless function) that serves `/api/lotcheck`; set `window.LOTCHECK_API` if the API lives on another origin, and replace the `Access-Control-Allow-Origin: *` header with the site's origin. The built-in rate limit is 30 requests/minute per IP and results are cached for an hour.

**Gotcha:** in this Bash tool, a double backslash in heredoc Python (e.g. `"\b"`) can arrive as a literal backspace character. Use the Edit/Write tools for any code with regexes.

## Plans, furniture and code check (2026-11-04)
- `src/plan.js` holds ONE room layout per size (`PLAN.layout(W,D)`). It drives the floor plan SVG, the window positions (`openingsFor` in adu.js calls it, so no window crosses a partition or corner), the 3D partitions and furniture, and `PLAN.check()`.
- Sizes supported: width 24 to 40, depth 16 to 28 (slider minimums raised; smaller sizes cannot hold comfortable furniture). D=16 is a studio (kitchen and bath on one wet wall, bed at the far end behind a wardrobe); D>=20 is one or two bedrooms.
- The check table covers room area/dimension, daylight 8%, ventilation 4%, bedroom egress, toilet and shower clearances, ceiling height, doors, alarms, solar and accessibility notes. Section numbers are IRC 2021 (CRC/ORSC adopt them). Solar (CA vs OR) and accessibility (CBC 11A for ADUs) are flagged as "confirm with the building department" because the sources disagreed.
- Test: a sweep over every supported size must show no `validate` errors, no failed rows (overlaps, egress, daylight). Run it in the page console.

## Performance and services (2026-11-05)
- `src/perf.js`: envelope comparison, code minimum vs a proposed high-performance package (R-30 wall with 2 in exterior mineral wool, about R-50 roof, R-38 floor, triple glazing U-0.19, 1.0 ACH50, heat-recovery ventilator, heat pump heating and water, all electric). It computes UA, a design-day heating load and an upper-bound annual heating energy from the unit's own areas and openings. Code values come from the 2023 ORSC Table N1101 and the 2025 California Energy Code prescriptive tables as summarised in public sources; the Oregon air-leakage limit is reported as 3 or 4 ACH50 and 4 is used. It is NOT a Title 24 / REScheck / PHPP run. The high-performance assemblies are proposals to confirm with Pacific Wall. Pricing adds a PLACEHOLDER uplift (`PRICING.perf`, $14/sf + $4,500 on the kit); the Performance chip switches it.
- Exterior insulation adds about 2 in to the wall and is not drawn in the 3D model (panel thickness is still 6.5 in).
- `PLAN.mep(W,D)` (plan.js) routes services from the layout: one mechanical core (a MECH closet in the studio, UTIL in the others; the two-bedroom plan gets a UTIL closet off the living area), a service-ceiling raceway with power and data lanes, wet-wall supply, floor-zone drains with hatches and a cleanout, refrigerant and ventilation lines, heat pump heads, leak sensors, and an outdoor service side. The Services chip shows it on the plan (colour coded, with a legend and notes) and as an x-ray in 3D (`addServices` in adu.js). Routes are typical and schematic; the trades size them.
- Sweep to run after any layout change: every size from 24x16 to 40x28 must give no `validate` errors, no failed check rows, and `PLAN.mep` and `PLAN.svg(p,{mep:true})` must not throw.

- **Keep this design** (`src/tease.js` + `outreach/outreach.py`): email form in the library viewer and on the splash. `POST /api/tease` validates, logs the lead to `data/leads.jsonl`, and writes a complete email (dusk render inline, lot-fit note if an address was given, 3-step "what happens next", a one-tap "when are you thinking?" row) to `data/outbox/*.eml` + `.html`. **Nothing is sent** unless `WWA_SMTP_HOST/PORT/USER/PASS` are set. Set `WWA_BASE_URL` (links), `WWA_FROM`, and `WWA_POSTAL` (street or PO box for the footer: required for real sending). Each letter has a unique 6-character code, a personal lot diagram, and a QR to `<base>/l/<CODE>`. Addressed "Current Resident" unless the CSV has names.
- **Splash** (`src/splash.src.html` -> `splash.html`, served at `/l/<CODE>`; `/l/` alone is the generic page): the letter's address as the headline, the stored lot plan and fit table, the three PL homes with "fits your lot" badges and a live 3D model, the keep-it form, and a link to the full live report. No prices (the rates are still placeholders). `GET /api/letter/<code>` returns only the site address, lot result and fit.
- **Before real mailing:** the site must be live at the `--base` URL (the QR leads nowhere until then); `WWA_POSTAL` set; confirm the list (these candidates are drafts and may include renters or addresses you do not want); check city zoning (not connected, so "likely allowed" is the state baseline only). Printing: full-bleed banner needs a 0.125 in bleed from the printer.

## Launch fixes (2026-11-10)
- **Existing buildings in the fit check.** `lotcheck/server.py: structures()` reads FEMA / ORNL "USA Structures" footprints (public ArcGIS layer, satellite-derived) for the lot. `geom.fit_rect` and `envelope_cells` take `obstacles` + `obs_clear` and keep the unit **6 ft** from every building (`BUILDING_CLEAR_FT`, an assumption, not a code lookup). The report, splash and letter plans draw the buildings in grey. Limits: the data can be out of date (for example rebuilds after the 2020 Almeda fire), and a lot with no footprint is flagged "Needs review"; letters require at least one footprint on the lot. Geometry tests cover obstacles (`python lotcheck/test_geom.py`).
- **Size cap, not verified.** Each result carries `size_ok`: unit area <= min(800 sq ft, 75% of the biggest footprint's area). 800 sq ft / 75% is a typical Oregon city cap, NOT Phoenix's or Talent's: neither code could be read (talent.municipal.codes refuses automated fetches; the Phoenix PDF link 404s). Units over the cap show "may exceed size cap" and are never chosen as a letter's "best fit". Read the real codes (Talent TMC 18.165; Phoenix Land Development Code) and put the numbers in `server.py`.
- **Library hidden.** `python build.py` leaves out the library section, its nav link and its data unless `WWA_LIBRARY=1` (rights to show other architects' redrawn plans are unsettled).
- **Lead alerts.** Every submission writes `data/notify/*.txt` and, when SMTP is configured, emails `WWA_NOTIFY` (default the From address). `python outreach/report.py` prints letters opened, leads, clicks, "when are you thinking" answers, unsubscribes, and writes `data/leads.csv` (ignores @example.com test entries).
- **Email compliance.** One-click `/u/<token>` unsubscribe (`data/suppress.txt`; suppressed addresses get nothing), `List-Unsubscribe` headers, `/privacy` page (plain-language draft: have it reviewed), and real sending is refused until `WWA_POSTAL` is set. Set up SPF, DKIM and DMARC on the sending domain.
- **Behind a proxy**, set `WWA_TRUST_PROXY=1` so rate limits and hashed visitor codes use `X-Forwarded-For`.
